# Config Service

`CrudConfigService` is the main programmatic API for reading and writing config values.

Typical operations:

- `get` — read a single value
- `getList` — list values in a section / environment
- `set` — upsert value
- `delete` — delete value

## Example

```typescript filename="my-config.service.ts" copy
import { Injectable } from "@nestjs/common";
import { CrudConfigService } from "@elsikora/nestjs-crud-config";

@Injectable()
export class MyConfigService {
 constructor(private readonly configService: CrudConfigService) {}

 async setupApplicationConfig() {
  await this.configService.set({
   section: "api-settings",
   name: "API_KEY",
   value: "my-secret-api-key",
   description: "Production API key",
   environment: "production",
  });

  const apiConfig = await this.configService.get({
   section: "api-settings",
   name: "API_KEY",
   environment: "production",
   shouldLoadSectionInfo: true,
   useCache: true,
  });

  return apiConfig;
 }

 async getConfigurationList() {
  return await this.configService.getList({
   section: "api-settings",
   environment: "production",
   useCache: true,
  });
 }

 async deleteConfiguration() {
  await this.configService.delete({
   section: "api-settings",
   name: "API_KEY",
   environment: "production",
  });
 }
}
```

## Caching

Caching is controlled by:

- global `cacheOptions.isEnabled` (module options)
- per-call `useCache` flag (`get` / `getList`)

## Encryption

When `encryptionOptions.isEnabled` is enabled, values are encrypted on `set()` and decrypted automatically on `get()`/`getList()` when `isEncrypted` is true.

## Transaction ownership

`set()` called without `eventManager` owns a named `crud-config-set` Automator transaction. All methods also accept the exact `EntityManager` already bound to an active Automator owner. In a transaction-enabled migration, pass the callback manager to every config operation:

```typescript copy
await configService.set({
 section: "app-settings",
 name: "APP_NAME",
 value: "My Application",
 eventManager: entityManager,
});
```

`eventManager` is join-only in Automator 4. It does not establish context for an arbitrary manager from a raw TypeORM transaction. Omitting it inside a transaction-enabled migration would make `set()` attempt a nested owner, which Automator rejects. This ownership contract is unchanged from CrudConfig 3.

When migration `useTransaction` is `false`, callbacks receive `undefined`. Each standalone `set()` still owns its own atomic transaction, but several migration writes do not share one all-or-nothing unit.

## Duplicate protection

The database unique constraint owns ConfigData duplicate protection across `name`, `environment`, and `section`. Automator maps conflicting generated creates and updates to `409 CONFIGDATA_DUPLICATE_KEY`.

CrudConfig 4 does not export or register the old ConfigData before-insert event/listener/subscriber pipeline and does not require consumer `EventEmitterModule` wiring. Application-specific validation and auditing belong in the application's service or Automator lifecycle layer.

## Working with multiple environments

```typescript filename="multi-env.service.ts" copy
import { Injectable } from "@nestjs/common";
import { CrudConfigService } from "@elsikora/nestjs-crud-config";

@Injectable()
export class MultiEnvironmentService {
 constructor(private readonly configService: CrudConfigService) {}

 async setupEnvironmentConfigs() {
  const environments = ["development", "staging", "production"];

  for (const env of environments) {
   await this.configService.set({
    section: "database",
    name: "DATABASE_URL",
    environment: env,
    value: `postgres://localhost:5432/${env}_db`,
    description: `Database URL for ${env} environment`,
   });
  }
 }
}
```
